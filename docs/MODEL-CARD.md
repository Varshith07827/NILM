# Model Card — `nilm-mobilenetv3-small`

## Overview

| | |
|---|---|
| **Task** | Multi-label appliance detection from aggregate mains current |
| **Architecture** | MobileNetV3-derived CNN (depthwise separable, inverted residual, squeeze-excite, hard-swish) |
| **Parameters** | 104,446 |
| **Input** | `(8, 34, 1)` — 8 consecutive 1-second windows × 34 electrical features |
| **Output** | 12 independent sigmoids, one per appliance |
| **Size** | 408 KB float32 · 222 KB TFLite float16 · ~102 KB int8 |
| **Inference** | ~2.1 ms per window on the NumPy kernel (CPU) |
| **Training data** | 72,000 simulated windows across 180 episodes |
| **Licence / provenance** | Trained from scratch on data generated by this repository |

---

## Intended use

Detecting which of twelve modelled household appliances are **drawing power** in a
given second, from a single-point current measurement, within the simulation
environment in this repository.

### Out of scope

- **Real mains deployment without fine-tuning.** Trained purely on synthetic data.
- **Appliances outside the catalogue.** The output layer is fixed at twelve classes.
- **Distinguishing identical appliances.** Two identical fans are indistinguishable
  from one fan at double amplitude — a physical limit of single-point sensing,
  not a model deficiency.
- **Billing of record.** Appliance-level figures are estimates, not sub-metered
  measurements.

---

## Input features

34 values per second, in three families. **No time-of-day feature is included** —
letting the model learn household habits would inflate accuracy without
demonstrating disaggregation.

| Family | Features |
|---|---|
| Steady state (11) | `i_rms`, `i_peak`, `i_mean_abs`, `crest_factor`, `form_factor`, `v_rms`, `real_power_w`, `apparent_power_va`, `reactive_power_var`, `power_factor`, `displacement_pf` |
| Harmonic (15) | `fundamental_a`, `thd`, `harmonic_ratio_{3,5,7,9,11,13}`, `harmonic_amp_{3,5,7,9,11,13}`, `spectral_centroid_hz` |
| Transient (8) | `cycle_rms_std`, `cycle_rms_range`, `inrush_ratio`, `delta_power_w`, `delta_reactive_var`, `delta_i_rms`, `delta_thd`, `event_magnitude` |

Inputs are standardised with a per-feature mean and standard deviation computed on
the **training split only** and frozen into the exported artefact, so the edge
runtime standardises identically.

---

## Labels

Multi-label binary: for each appliance, whether it is **actually drawing power**
in the final second of the sequence.

Note the distinction from "switched on at the socket". A refrigerator between
compressor cycles is switched on but is not drawing, and the model is expected to
say so. Threshold: drawing more than 5 % of rated power.

---

## Training

| | |
|---|---|
| Data | 72,000 windows, 180 episodes of 400 s |
| Episode mix | 65 % unconstrained random appliance combinations (coverage), 35 % realistic scenario behaviour |
| Split | **By episode**, 80/20 — never by window |
| Loss | Binary cross-entropy with per-appliance positive class weighting, `clip((1−p)/p, 0.5, 8)` |
| Optimiser | Adam, lr 2 × 10⁻³, `ReduceLROnPlateau` (×0.4, patience 2), early stopping on val AUC (patience 5) |
| Batch size | 256 |
| Epochs | 18 (all completed) |
| Training time | 444 s on CPU |
| Seed | 20240501 |

**Why split by episode:** adjacent one-second windows are near-identical.
Splitting randomly across windows puts almost-duplicate samples on both sides of
the split and produces a meaninglessly optimistic validation score.

**Why random-combination episodes:** without them the model would never see a
microwave and a washing machine running together, and would quietly learn the
household's habits instead of its electrical signatures.

**Why class weighting:** a microwave draws power a couple of percent of the day.
Unweighted, predicting "off" forever scores 98 % and the network settles there.

## Decision thresholds

Tuned **per appliance** on the validation split to maximise F1, rather than a
blanket 0.5. Multi-label problems with very different base rates are poorly served
by a single global threshold.

| Appliance | Threshold | Appliance | Threshold |
|---|---|---|---|
| Ceiling Fan | 0.34 | Washing Machine | 0.92 |
| LED Light | 0.33 | Air Conditioner | 0.19 |

## Backend equivalence

Verified automatically at export time by `ai/export.py::verify_export`:

| Comparison | Max abs. difference | Mean abs. difference |
|---|---|---|
| Keras → NumPy kernel | 8.3 × 10⁻⁶ | 1.4 × 10⁻⁷ |
| Keras → TFLite (float16) | 8.4 × 10⁻³ | — |

`ai/train.py` exits with an error if the Keras↔NumPy maximum difference exceeds
1 × 10⁻³, so a model whose edge runtime has silently diverged cannot be shipped.

## Limitations and failure modes

1. **Small loads under large ones.** The two weakest classes (LED light, mobile
   charger — 9 W and 12 W) fail most often when a kilowatt-scale load is running.
   Their contribution is close to the modelled 8 mA sensor noise floor. Physical,
   not fixable by tuning.
2. **Harmonically similar loads compete.** LED light and tube light are both
   non-PFC lighting drivers with similar harmonic shape. The classifier separates
   them well, but the disaggregator's columns are near-collinear, which is why the
   attribution prior is centred on classifier confidence rather than zero
   (see below).
3. **Synthetic training data.** Real mains carries interference, appliance-to-appliance
   manufacturing variation and ageing effects absent here.
4. **Duty-cycled appliances have a detection lag.** The model reads an 8-second
   sequence, so a compressor restarting takes a couple of seconds to register.
   Measured mean detection latency is ~0.5 s in the live pipeline.
5. **Fixed catalogue.** New appliances require retraining.

### A resolved failure mode, documented

An earlier version centred the disaggregator's Tikhonov prior at zero. Because an
LED lamp and a tube light are nearly collinear columns in the signature matrix,
least squares resolved the ambiguity by driving the smaller load to **exactly 0 W
while the classifier still reported it as detected** — an appliance shown as "on,
drawing nothing", which is worse than either answer alone.

The fix was to centre the prior on the classifier's own confidence:
*"if the model is 95 % sure this is running, expect it near rated draw, but let
the harmonic evidence override that."* Collapses fell to 0.47 % of detections.
Covered by a regression test
(`test_ai.py::TestDisaggregation::test_a_confident_detection_is_never_assigned_zero`).

## Baseline comparison

`ai/inference.py` includes a training-free classical baseline: non-negative least
squares matching of harmonic phasors over all twelve appliances at once. It is a
genuine algorithm — essentially what NILM looked like before neural networks — and
serves as the fallback when no trained model is present. It fails in an
instructive way: with no access to transients, it confuses combinations of small
loads with single larger ones.

## Reproducing

```bash
python -m pip install -r requirements-train.txt
python -m ai.train --windows 72000 --epochs 18 --seed 20240501
```

Artefacts are written to `ai/artifacts/`: `nilm_model.keras`,
`nilm_model.tflite`, `nilm_weights.npz`, `nilm_model.json` and
`training_report.json` (the full per-appliance evaluation used above).
